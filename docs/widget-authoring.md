# The route from a widget idea to a merged widget

You have an idea and no files. This is the order to do things in, and why that
order.

Everything here is already written down somewhere — the layer rules in
[`AGENTS.md`](../AGENTS.md), the store layers and the bundle in
[architecture.md](architecture.md), the render budgets in
[rendering.md](rendering.md), the migrations in
[settings-schema.md](settings-schema.md). None of those answers the question you
start with: _what do I do first, and how do I know when I am done?_ This does.
Where a rule lives elsewhere, this page links to it and does not restate it —
two copies of a rule is one rule and one lie.

The steps are ordered **by cost, not by file layout**. The expensive decisions
come first, because reversing one late invalidates the panel, the stories and
the budget written against it. The mechanical files come last, because redoing
them is cheap.

Every step names **what enforces it** — a lint rule, a test, the budget suite,
or nothing at all. A step enforced by nothing is marked as such, because you
have to be able to tell a convention from something that fails the build.

The acting half of this route is the **`new-widget` skill**
(`.claude/skills/new-widget/`): the same steps as imperatives, which asks the
decisions and writes the files. This page is the reasoning behind it.

---

## What you do not have to do

Read this before step 1, because most of the fear about "shared files I have to
remember to edit" is unfounded.

| You might think you must      | You do not, because                                                                                                                                                                                                                            |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Register the widget somewhere | `manifest.ts` is collected by glob into `WIDGETS` / `WIDGET_BY_ID` / `DEFAULT_WIDGETS` (`store/widget-catalog.ts`)                                                                                                                             |
| Register the component        | `mount.ts` is collected by glob into `WIDGET_COMPONENTS` (`ui/widgets/registry.ts`)                                                                                                                                                            |
| Register the settings panel   | The panel's own `PANEL_WIDGET_IDS` export is collected by glob (`WidgetSettings/panels/panel-registry.ts`)                                                                                                                                     |
| Write a settings migration    | `mergeWithDefaults` runs after the migration chain over `defaultWidgets[]` and every `layouts[].widgets[]` — **a new setting with a default needs no migration** ([settings-schema.md → When you do NOT need a migration](settings-schema.md)) |
| Renumber the other widgets    | `order` is spaced by ten; a manifest with no `order` sorts last, and equal numbers tie on id                                                                                                                                                   |
| Hand-write a backend type     | `src/types/bindings.ts` is generated by specta — never edit it, and never duplicate a shape from it                                                                                                                                            |

So a new widget edits **no shared file** except `src/types/widget-settings.ts`,
which needs your settings interface and its entry in the `WidgetSpecificSettings`
union — a union cannot be built by a glob.

## Step 1 — Telemetry: does the field exist, at what rate, and is it gated?

**First, before markup.** A widget built against a field the sim does not carry
is not fixable by editing the widget. This is the step whose absence is most
expensive.

Three questions, in order.

**Does the field exist?** Offline, the answer is `src/types/bindings.ts` — the
generated contract, and the only honest list. Against a live sim, it is the
**Telemetry Inspector** (Settings → Maintenance): it browses the raw
`SourceFrame`, which is a _superset_ of the bundle — every field the adapter
produced, including ones no widget receives — and the parsed session snapshot
beside it. If a field is in the inspector but not in the bundle, it exists and
is not published; that is a backend ticket, not a widget one.

If the field does not exist at all, you are on a different route: adding a field
to the contract is the backend half — `sources/`, `computations/`, a specta
type, a bundle tier — and lives in
[architecture.md → Part I](architecture.md). Come back here when the field
lands.

**At what rate does it arrive?** [architecture.md → Rate tiers](architecture.md)
carries the table. In short: 60 Hz is `carDynamics`, `carInputs`, `carPositions`,
`lapDelta`, `pitTarget`; 10 Hz is `carIdx`, `chassis`, `lapTiming`, `proximity`,
`driverEntries`; 4 Hz is `carStatus`, `fuel`, `pitStops`; 1 Hz is `session` and
`environment`. The rate decides how you decompose (step 3) and whether you owe a
budget test (step 8).

**Never** integrate 60 Hz against telemetry `sessionTime` — use
`performance.now()`.

**Is it demand-gated?** Seven fields are filled only while a widget asks for
them: `carDynamics`, `carInputs`, `carPositions`, `lapDelta`, `driverEntries`,
`relative`, `proximity`. A widget that reads one without declaring it in its
manifest **renders empty in the app and correct in Storybook** — the failure
mode this step exists to prevent. Declaring one you do not read costs every
other window the traffic. See
[architecture.md → Demand gating](architecture.md).

> _Enforced by:_ nothing checks that you declared what you read, or that you read
> what you declared. `budget-coverage.perf.test.tsx` does check that every field
> you declare is one the perf burst knows how to move — which catches a typo,
> not an omission. The rest is on you and on review.

## Step 2 — Does it need a store?

Answer by the rule, not by taste.

**Create a widget store only when the widget has UI state, timers, or non-trivial
derived logic.** Simple widgets read the data stores directly, and stay simple.

- Shared derived logic used by two or more widgets → a `computed` on the **data**
  store, not duplicated in two widget stores.
- Derived values are `computed` getters in a store — never `useMemo` in a
  component.
- Hooks are for the DOM and the browser only. Everything else is a store.
- Widget stores read the **original** copy (`firstWidgetOfType`): one store per
  app cannot be per copy, and what a store holds is computation, not
  presentation.

The full six rules are [architecture.md → The six store rules](architecture.md).

If the answer is no, the widget's file list is one file shorter and this step
cost you nothing. That is the point of asking it before writing anything.

> _Enforced by:_ the layer direction is, by `no-restricted-imports` in
> `.oxlintrc.json` — a store reaching into `@ui/**` fails `npm run lint`. Whether
> you _needed_ the store is not enforced.

## Step 3 — The shape: what reads what, and how big is it

Three decisions, all cheaper now than after the SCSS exists.

**Design size.** `designWidth` / `designHeight` in the manifest are the
coordinates every `ws()`, `fs()` and `sp()` is measured against;
`WidgetContainer` sets `--wfs = currentWidth / designWidth` and everything scales
from it. If the widget has toggleable columns, `designWidth` tracks the visible
set through `makeColumnLayoutResolver` and a `compute…DesignWidth` in the
widget's `*-utils.ts` — see `CloseBattleWidget` for the worked case.

**Decomposition.** `WidgetName.tsx` is a thin orchestrator. Every component is
`observer()` — root, sub-components, leaves — and every component reads the store
it needs **directly** rather than taking derived primitives as props;
dereferencing a value into a prop kills reactivity downstream.

**Where the hot field is read.** The root must not read a 60 Hz field. The
component that does returns as little as possible, and everything a hot value
does not change is created by a parent that does not re-render and arrives as
`children`. Splitting into smaller components does **not** help — the parent
still allocates every child element. This is the whole of
[rendering.md → The rule](rendering.md), and it is the one rule here that is
measured rather than reviewed.

> _Enforced by:_ the layer imports, by lint. The rendering rule, by the budget
> suite (step 8). Decomposition style, by review.

## Step 4 — Check the toolbox before writing a helper

There are roughly 30 helper modules, 14 shared components and 9 shared hooks.
[**docs/widget-toolbox.md**](widget-toolbox.md) lists all of them with one line
each on when to reach for it, plus the design tokens and the rule for where a new
helper belongs.

Read it. The cost of not reading it is a fifth lap-time formatter.

> _Enforced by:_ `docs/widget-toolbox.test.ts` keeps the catalogue complete — a
> module in the tree and not on the page fails `npm test`. Nothing stops you
> writing a duplicate helper.

## Step 5 — Settings: the interface, then the defaults

Two files, in this order.

1. `src/types/widget-settings.ts` — an `interface <Name>WidgetSettings`, and its
   entry in the `WidgetSpecificSettings` union. **The only shared file a new
   widget edits.**
2. The `userSettings` block in your manifest — `enabled`, `x`, `y`,
   `currentWidth`, `currentHeight`, then `...COMMON_WIDGET_DEFAULTS` and the
   appearance defaults from `ui/widgets/widget-manifest.ts`, then your own.

Add a setting **only if the widget uses it**. A widget with settings it does not
read is worse than a widget with none: it is a promise to the driver that the
switch does something.

No migration is needed for any of this — `mergeWithDefaults` fills a new key with
its default on the next load, over `defaultWidgets[]` and every layout's widgets.
A migration is for a value that changes meaning, unit or place
([settings-schema.md → When you DO](settings-schema.md)).

> _Enforced by:_ `npm run typecheck` — a settings key the manifest declares and
> the interface does not, or the reverse, fails to compile.

## Step 6 — The two files that are the widget

Beside the components, in `src/ui/widgets/<Widget>/`:

**`manifest.ts`** — plain data, and it **never imports its own component**. It is
read by the _store_ layer at import time, by migrations, by `DEFAULT_WIDGETS` and
by node-side tests, none of which should drag a React tree in. It carries `id`,
`order`, `label`, `description`, `designWidth`, `designHeight`, `userSettings`,
`telemetryEvents` (step 1), and optionally `resolveLayoutChange`,
`requiredCapabilities`, `overflowVisible`.

**`mount.ts`** — `{ id, component }`, four lines. A second file rather than a
manifest field because the two change for unrelated reasons: the manifest when
the data moves, the mount when the rendering does, and a file edited for two
reasons is the file two branches collide on.

Both are collected by glob. Nothing else to register.

> _Enforced by:_ `src/ui/widgets/widget-manifest.test.ts` and
> `registry.test.ts` — an id that does not match its mount, or a duplicate, fails
> `npm test`.

## Step 7 — The settings panel and the story

**`<Name>SettingsPanel.tsx`** goes in
`src/ui/app/main/components/WidgetSettings/panels/` — _not_ beside the widget,
because the remote screen renders widgets through the mount registry in a plain
browser, and a mount carrying its Ant Design panel would ship the settings UI to
every phone on the LAN. It exports `PANEL_WIDGET_IDS` (usually one id), which is
what the glob picks up.

Rows bind themselves: call `panelRows<YourSettings>()` once per panel and use the
`SwitchRow` / `ColorRow` it returns with a `settingKey`. A toggle is one element,
not a `SettingRow` wrapping a `Switch` wrapping a read and a write. Controls with
their own logic — clamped numbers, unit conversion, `Segmented` — still spell
themselves out inside a `SettingRow`. Every block inside a `Card` gets a
horizontal divider.

**`<Name>Widget.stories.tsx`** — named `const` PascalCase exports, no default
export, no anonymous functions, always a background decorator, stores seeded via
`runInAction` in a decorator. Nothing that exists only for a story may be added
to `store/preview/`.

> _Enforced by:_ a missing `PANEL_WIDGET_IDS` is silent — the widget simply has
> no panel. This is one of the two steps that fail quietly; the other is step 1.

## Step 8 — The render budget, if you declared a hot field

If your manifest declares `carDynamics`, `carInputs`, `carPositions` or
`lapDelta`, the widget needs a `<Name>Widget.perf.test.tsx` beside it: a fixed
burst of frames replayed through a real store, asserting how many times each
component woke.

Two things that catch people:

- A component under a budget is declared `observer(function Name() { … })`, not
  as an arrow. The name is what the measurement is keyed by, and the harness
  refuses to report rather than mis-attribute an anonymous one. This is the one
  place the repo's arrow-function rule does not apply.
- Budgets are absolute numbers in a table in the test. Raising one is allowed and
  costs one line of justification beside it in the same commit.

How a target is chosen, and what the current numbers are, is
[rendering.md → Budgets](rendering.md).

> _Enforced by:_ `src/perf/budget-coverage.perf.test.tsx` — a widget whose
> manifest declares a hot field and whose folder has no `*.perf.test.tsx` fails.
> The suite is `npm run test:perf`, its own command with its own config; it is
> deliberately **not** part of `npm test` or the pre-commit hook, because it needs
> a real browser. On a pull request it is the blocking _Run Render Budgets_ step
> of the frontend job in `.github/workflows/reusable-quality.yml`.

## Step 9 — Run the checks

```bash
npm run typecheck
npm run lint          # oxlint --type-aware; layer direction lives here
npm test              # vitest; also runs on commit via lefthook
npm run test:perf     # only if step 8 applied
```

---

## Step 10 — Run it in the app and look at it

A green suite is not the finish line. The widget has to render under `--wfs`
scaling, over a transparent always-on-top overlay, in a window that is not
Storybook's. Everything before this step is necessary and none of it is that.

```bash
npm run tauri:dev
```

Then drive it through the Tauri MCP bridge — `driver_session` (action `start`,
port 9223), then `webview_screenshot`, `webview_find_element`,
`webview_interact`. Never test the UI in a plain browser: the overlay's
transparency, its scaling and its window are the things being checked.

Look for the three failures that only appear here:

1. **Empty widget** — a gated field read but not declared (step 1).
2. **Wrong scale** — a `rem`, a `vw`, or a raw px where a token belonged (step 4).
3. **A setting that does nothing** — declared in step 5, never wired in step 7.

> _Enforced by:_ nothing. This step is a habit, and it is the one that catches
> what the suite cannot.

---

## The short version

1. Does the field exist, at what rate, is it gated → declare `telemetryEvents`
2. Store, or no store
3. Design size, decomposition, where the hot field is read
4. Read [the toolbox](widget-toolbox.md) before writing a helper
5. Settings interface + union entry, then manifest defaults
6. `manifest.ts` and `mount.ts`
7. Settings panel (with `PANEL_WIDGET_IDS`) and a story
8. Perf test, if a hot field was declared
9. `typecheck`, `lint`, `test`, `test:perf`
10. `tauri:dev`, and look at it
