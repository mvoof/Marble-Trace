# The route from a widget idea to a merged widget

You have an idea and no files. This is the order to do things in, and why that
order.

Everything here is already written down somewhere — the layer rules in
[`AGENTS.md`](../AGENTS.md), the layers, the stores and the bundle in
[architecture.md](architecture.md), the hot/cold rendering split in
[rendering.md](rendering.md), the migrations in
[settings-schema.md](settings-schema.md). None of those answers the question you
start with: _what do I do first, and how do I know when I am done?_ This does.
Where a rule lives elsewhere, this page links to it and does not restate it —
two copies of a rule is one rule and one lie.

The steps are ordered **by cost, not by file layout**. The expensive decisions
come first, because reversing one late invalidates the panel and the stories
written against it. The mechanical files come last, because redoing them is
cheap.

Every step names **what enforces it** — a lint rule, a test, or nothing at all.
A step enforced by nothing is marked as such, because you have to be able to
tell a convention from something that fails the build.

The acting half of this route is the **`new-widget` skill**
(`.claude/skills/new-widget/`): the same steps as imperatives, which asks the
decisions and writes the files. This page is the reasoning behind it.

---

## What you do not have to do

Read this before step 1, because most of the fear about "shared files I have to
remember to edit" is unfounded.

| You might think you must        | You do not, because                                                                                                                                                                                                                                    |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Register the widget somewhere   | `manifest.ts` is collected by glob into `WIDGETS` / `WIDGET_BY_ID` / `DEFAULT_WIDGETS` (`entities/widget/widget-catalog.ts`)                                                                                                                           |
| Register the component          | `mount.ts` is collected by glob into `WIDGET_COMPONENTS` (`widgets/registry.ts`)                                                                                                                                                                       |
| Register the settings panel     | The panel's own `PANEL_WIDGET_IDS` export is collected by glob (`features/widget-settings/panel-registry.ts`)                                                                                                                                          |
| Write a settings migration      | A widget stores only the settings that differ from its manifest, so a new key is read from the manifest everywhere — **a new setting with a default needs no migration** ([settings-schema.md → When you do NOT need a migration](settings-schema.md)) |
| Pick a place in the widget list | Every list is alphabetical by label; a manifest declares no position                                                                                                                                                                                   |
| Write a settings type           | `SettingsOf<typeof X_SETTINGS.shape>` comes out of the slice's `settings-schema.ts`; there is no shared union to add it to                                                                                                                             |
| Hand-write a backend type       | `src/shared/contracts/bindings.ts` is generated by specta — never edit it, and never duplicate a shape from it                                                                                                                                         |

### The shared files you _do_ edit

These, and no more. They are here in one place because each of them is a
glob's blind spot, and all but the first fail quietly or late.

| File                                     | When                    | What happens if you forget                                                                                                                                      |
| ---------------------------------------- | ----------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `src/locales/{en,es,ru,zh}/widgets.json` | always                  | **Nothing fails** if all four lack it — the catalog and the panel show raw i18n keys. One language without a key the others have fails `widget-locales.test.ts` |
| `src/entities/widget/widget-frame.ts`    | a non-rectangular plate | Nothing fails; the widget just wears a rectangle                                                                                                                |
| `scripts/capture-widgets.mjs` (`SHOTS`)  | always                  | Nothing fails; the widget's picture is never taken (step 12)                                                                                                    |
| `README.md`                              | always                  | Nothing fails; the widget is not documented (step 12)                                                                                                           |
| `site/index.html`                        | always                  | Nothing fails; the widget is missing from the site (step 12)                                                                                                    |

## Step 1 — Telemetry: does the field exist, at what rate, and is it gated?

**First, before markup.** A widget built against a field the sim does not carry
is not fixable by editing the widget. This is the step whose absence is most
expensive.

Three questions, in order.

**Does the field exist?** Offline, the answer is `src/shared/contracts/bindings.ts` — the
generated contract, and the only honest list. The raw sim frames in it are
**snake_case** (`velocity_x`, `steering_wheel_angle`) — they keep kerb's names —
while the bundle envelope and every computed frame are camelCase (`AGENTS.md`
→ Rust Backend). Search for a raw field in snake*case. Against a live sim, the answer is the
**Telemetry Inspector** (Settings → Maintenance): it browses the raw
`SourceFrame`, which is a \_superset* of the bundle — every field the adapter
produced, including ones no widget receives — and the parsed session snapshot
beside it. If a field is in the inspector but not in the bundle, it exists and
is not published; that is a backend ticket, not a widget one.

If the field does not exist at all, you are on a different route: adding a field
to the contract is the backend half — `sources/`, `computations/`, a specta
type, a bundle tier — and lives in
[architecture.md → Part I](architecture.md). Come back here when the field
lands.

**At what rate does it arrive?** [architecture.md → Rate tiers](architecture.md)
carries the table. In short: 60 Hz is `carDynamics`, `carInputs`, `carPositions`,
`lapDelta`, `pitTarget`, `coach`; 10 Hz is `carIdx`, `chassis`, `lapTiming`,
`proximity`, `driverEntries`, `paceCar`; 4 Hz is `carStatus`, `fuel`, `pitStops`; 1 Hz is `session` and
`environment`. The rate decides how you decompose (step 3) and whether you owe a
budget test (step 9).

**Never** integrate 60 Hz against telemetry `sessionTime` — use
`performance.now()`.

**Is it demand-gated?** The gated fields are the
exports of `src/shared/contracts/telemetry-event-bits.ts` (generated from
`src-tauri/src/model/telemetry_events.rs`) — **read that file, it is the list**,
and it grows. At the time of writing it holds ten:
`carDynamics`, `carInputs`, `carPositions`, `lapDelta` (the 60 Hz four, the
**hot** ones), then `driverEntries`, `relative`, `proximity`, `incidents`, `coach`, `safetyRating`.

A widget that reads a gated field without declaring it in `telemetryEvents`
**renders empty in the app and correct in Storybook** — the failure mode this
step exists to prevent. Declaring one you do not read costs every other window
the traffic. See [architecture.md → Demand gating](architecture.md).

**Does the sim have to support it?** Separately from the mask,
`requiredCapabilities` in the manifest hides the widget from the catalog when the
connected sim cannot feed it (`availableWidgetIdsOf` in
`entities/widget/widget-availability.ts`). It names keys of
`CapabilitiesPayload`, not telemetry fields: a widget reading `carDynamics` or
`carInputs` for the player's own car declares `['playerDynamics']`; the others in
use are `chassis`, `fuel`, `inputs`, `radar`, `relative`, `sectors`,
`standings`, `weatherCurrent`. Omitting it is not an error — the widget is simply
offered on sims that cannot fill it, and renders empty there.

> _Enforced by:_ nothing. No check confirms you declared what you read, or that
> you read what you declared — it is on you and on review.

## Step 2 — Does it need a store?

Answer by the rule, not by taste.

**Create a widget store only when the widget has UI state, timers, or non-trivial
derived logic.** Simple widgets read the entity stores directly, and stay simple.

- Shared derived logic used by two or more widgets → a `computed` on the **data**
  store, not duplicated in two widget stores.
- Derived values are `computed` getters in a store — never `useMemo` in a
  component.
- Hooks are for the DOM and the browser only. Everything else is a store.
- A new widget store is **per instance**: declare it in `mount.ts`
  (`store: (context) => new XWidgetStore(context)`), read settings with
  `getSettings(context.instanceId)`, and give components a hook over
  `useWidgetInstanceStore`. It exists only while the instance is mounted. A
  shared store it reads (`flags`, `radar`) goes in `sharedStores`.
  A reaction or timer that would overwrite what a preview seeds by hand starts
  only when `context.core.startsWidgetStores`. `StandingsWidget` and `InputTraceWidget`
  are the worked examples; `WheelToWheelWidget` for a store that also decides
  the auto-hide.

The full six rules are [architecture.md → The six store rules](architecture.md).

If the answer is no, the widget's file list is one file shorter and this step
cost you nothing. That is the point of asking it before writing anything.

**Done when:** you can name, in one sentence, where each value the widget draws
comes from — an entity store getter, a pure helper, or the widget store you just
decided to write. If any value has no owner yet, the step is not finished.

> _Enforced by:_ the layer direction is, by `no-restricted-imports` in
> `.oxlintrc.json` — an entity or a feature reaching into `@widgets/**` fails `npm run lint`. Whether
> you _needed_ the store is not enforced.

## Step 3 — The shape: what reads what, and how big is it

Three decisions, all cheaper now than after the SCSS exists.

**Design size.** `designWidth` / `designHeight` in the manifest are the
coordinates every `ws()`, `fs()` and `sp()` is measured against;
`WidgetContainer` sets `--wfs = currentWidth / designWidth` and everything scales
from it. If the widget has toggleable columns, `designWidth` tracks the visible
set through `makeColumnLayoutResolver` and a `compute…DesignWidth` in the
widget's `*-utils.ts` — see `CloseBattleWidget` for the worked case.

If a setting decides the design width — a column toggle, or an orientation switch
with one width per orientation — the manifest declares **two** things, not one:
`resolveLayoutChange` to rescale `currentWidth` on the toggle, and
`deriveDesignWidth` so the width is recomputed rather than trusted every time the
widget is installed. The stored width is a cache of arithmetic the settings
already answer, and shipping only the resolver is how the weather widget came to
render at 1.7× and grow on every click. See "Toggleable-column widgets" in
`docs/architecture.md`.

**The layout knobs.** Design size is not the only thing the manifest decides
about shape, and the rest are easy to miss because they are all optional:
`autoHeight`, `lockAspectRatio` (resize keeps the ratio — for a circular plate),
`scaleFromHeight` (`--wfs` follows the height instead, for a widget whose middle
grows horizontally), `contentSized` (the plate is as wide and tall as what it
draws), `overflowVisible` and `transparentContainer`. Read the
doc comments on `WidgetMeta` in `src/shared/contracts/widget-settings.ts` — they are short
and they are where these are actually explained. A plate that is not a rectangle
also needs a case in `widgetFrameBorderRadius` (`src/entities/widget/widget-frame.ts`).

**Resize handles follow what can change.** A widget is offered only the
handles that change something it draws (`resizeDirectionsFor` in
`widget-frame.ts`, shared by the overlay and the layout editor): all eight for
a plate that stretches both ways, `e`/`w` for an `autoHeight` one, and **only
the corners for a `contentSized` one** — it stretches in neither axis, so a drag
can only scale it. A plate sized by its content (a column that leaves the row
narrows it) declares `contentSized` with `transparentContainer` and paints its
own ground from `--widget-bg`; its frame then hugs the plate, the corner drag
scales from the drawn box so the corner follows the pointer, and snapping
measures the drawn size. `widget-catalog.test.ts` fails a `contentSized`
widget that does not paint its own plate.

**Decomposition.** `WidgetName.tsx` is a thin orchestrator. A component that
**reads a store** is `observer()`, and it reads that store **directly** rather
than taking derived primitives as props — dereferencing a value into a prop kills
reactivity downstream. A purely presentational shell that takes only props need
not be an observer; `WidgetPanel` and `SettingRow` are plain arrow functions for
exactly that reason.

**Where the hot field is read.** Branch here, because the two answers produce
different widgets:

- **One number (or a handful) per frame, driving a position, a width or a color.**
  Do not render it in React at all — `useReactiveDomWrite` writes the value
  straight to a DOM node or a CSS custom property inside `requestAnimationFrame`,
  and the component wakes zero times. This is the 60 Hz escape hatch
  ([rendering.md → The escape hatch](rendering.md)), and for a single-number
  widget it is the intended answer, not an optimisation to reach for later.
- **A subtree whose shape changes** — rows appearing, a list reordering. Then the
  React rule applies: the root must not read the hot field, the component that
  does returns as little as possible, and everything the hot value does not
  change is created by a parent that does not re-render and arrives as
  `children`. Splitting into smaller components does **not** help — the parent
  still allocates every child element. [rendering.md → The rule](rendering.md).

**Done when:** you can name the component that reads the hot field, and say which
of those two branches it is on — this is what step 9 checks by review.

> _Enforced by:_ the layer imports, by lint. The rendering rule, by review at
> step 9. Decomposition style, by review.

## Step 5 — Settings: the schema, then the defaults

One description per setting, in the widget's slice (ADR-0008).

1. `settings-schema.ts` beside the manifest —
   `export const <NAME>_SETTINGS = defineSettings('<locale block>', { … })`
   with the builders of `shared/lib/widget-settings-dsl.ts`: `bool`, `num`
   (with `min` / `max` / `step` — out-of-range values are clamped on load),
   `choice` (string or number members; a choice several widgets share comes
   from `shared/contracts/widget-choices.ts`), `color`, `numRecord`,
   `nullable(field)`. Export the type as
   `SettingsOf<typeof <NAME>_SETTINGS.shape>`. Every setting has a default, so
   none is optional and no read needs `?? fallback`.
2. The `userSettings` block in your manifest — `enabled`, `x`, `y`,
   `currentWidth`, `currentHeight`, then `...COMMON_WIDGET_DEFAULTS` and the
   appearance defaults from `widgets/widget-manifest.ts`, then
   `...<NAME>_SETTINGS.defaults` — and `settingsSchema: <NAME>_SETTINGS` on the
   manifest itself.

Add a setting **only if the widget uses it**. A widget with settings it does not
read is worse than a widget with none: it is a promise to the driver that the
switch does something.

Ask of every setting: **could it hold two different values on the driver's
monitor and on a stream screen at once?** Every instance has its own settings,
so a widget setting is a per-screen setting. Colours, columns, thresholds a
readout warns at — yes, they belong here. Anything that acts on the car or the
sim — the pit-stop auto rules, the fuel key step, the car length — cannot
differ between two screens for one car. It goes in `appSettings`
(`entities/app-settings/app-settings.store.ts`), on a page under Settings, and the
widget only shows it; the pit strategy (`shared/contracts/pit-strategy.ts`) is the worked
example. A copy left in a widget panel is a switch the stream screen offers and
then ignores.

No migration is needed for any of this — a widget stores only what differs from
its manifest, so a new key is read from the manifest in every template and every
instance.
A migration is for a value that changes meaning, unit or place
([settings-schema.md → When you DO](settings-schema.md)).

> _Enforced by:_ `widget-catalog.test.ts` — a manifest without a schema, or a
> default that fails its own schema's check, fails `npm test`. Every value read
> from `settings.json` or written by a panel passes `checkedSettings`: a wrong
> type falls back to the default, a number out of range is clamped.

## Step 6 — The two files that are the widget

Beside the components and the schema, in the widget's slice `src/widgets/<name>/`
(kebab-case; the components inside stay PascalCase):

**`manifest.ts`** — plain data, and it **never imports its own component**. It is
read by the catalogue in `entities/widget` at import time, by migrations, by `DEFAULT_WIDGETS` and
by node-side tests, none of which should drag a React tree in. It carries `id`,
`label`, `description`, `designWidth`, `designHeight`, `userSettings`,
`telemetryEvents` and `requiredCapabilities` (step 1), the layout knobs from
step 3, and optionally `resolveLayoutChange`.

The widget's place in every list follows from its `label` — lists are
alphabetical, so there is no position to pick.

**`mount.ts`** — `{ id, component }`, four lines. A second file rather than a
manifest field because the two change for unrelated reasons: the manifest when
the data moves, the mount when the rendering does, and a file edited for two
reasons is the file two branches collide on.

Both are collected by glob. Nothing else to register.

> _Enforced by:_ `src/widgets/widget-manifest.test.ts` and
> `registry.test.ts` — an id that does not match its mount, or a duplicate, fails
> `npm test`.

## Step 7 — Strings, in four languages

Nothing in the manifest reaches the driver's eyes. The catalog description and
every label in the settings panel are i18n keys, looked up in
`src/locales/{en,es,ru,zh}/widgets.json`:

```
catalog.<widget-id>.description
settingsPanels.<locale block>.<setting>       # the row's title
settingsPanels.<locale block>.<setting>Desc   # its description, optional
settingsPanels.<locale block>.<setting>_<member>   # a choice's members
```

The catalog description is **one short sentence, two at most, and no longer
than 80 characters in any language**. The widget list clamps it to three lines,
and a description cut off mid-word tells the driver less than a short one; the
settings panel is where a widget explains itself, row by row.

The locale keys **are the setting keys**, so a schema field needs no label of
its own; a field takes a `label` only to borrow a `common.*` string several
widgets share. All four files, or the driver reads a raw key where a label
should be.

> _Enforced by:_ `widget-locales.test.ts`, partly — a key in one language and
> not the others fails, and so does a block left behind by a deleted widget, or a
> catalog description over 80 characters. A
> widget whose strings are missing from all four fails nothing; it is the
> quietest step on the route, which is why it has one of its own.

## Step 8 — The settings panel and the story

**`<Name>SettingsPanel.tsx`** goes in the widget's own slice, and is **not**
imported by `mount.ts`: the remote screen renders widgets through the mount
registry in a plain browser, and a mount carrying its Ant Design panel would ship
the settings UI to every phone on the LAN. Main's panel registry finds it by glob.

**Copy `GMeterSettingsPanel.tsx`** rather than assembling one from the rules —
it is short and shows both kinds of row: `<Row>` from `schemaRows`, and one
control written out by hand with `useWidgetEditor()`,
`usePanelWidgetId(fallbackId)` and `useLabels`.

Two constraints that are not visible from the file you copy:

- It must export `PANEL_WIDGET_IDS` (usually one id) — that is what the glob
  keys on.
- It must export **exactly one component**. `panelOf` in `panel-registry.ts`
  takes the first export that is not `PANEL_WIDGET_IDS`, so a second exported
  component silently registers the wrong one.

Rows read the schema: call `schemaRows(<NAME>_SETTINGS)` once per panel and
write `<Row setting="…" />` — the control follows the field's kind (switch,
colour, segmented, slider; `stacked`, `input` to adjust), the labels follow the
setting key. Controls with their own logic — a unit in a slider's tooltip, a
segmented control whose labels are not the members — still spell themselves out
inside a `SettingRow`, with their texts from `useLabels`. Blocks inside a `Card` are separated
automatically by `.cardContent > * + *` — **do not add dividers by hand.**
A row that only qualifies another takes `dependsOn` (or goes in a
`DependentBlock` from `panelRows<Settings>()`) and sits directly after its parent — never
`{settings.x && …}` in the panel.

**`<Name>Widget.stories.tsx`** — spread `defineWidgetStories({ widget, size,
seed, seedSnapshot, args, argTypes })` from
`@/storybook/define-widget-stories`, which mounts the widget
with its background and does the `runInAction` seeding for you. The widget's
settings appear on the Controls tab by themselves, read from the manifest and
its schema (a choice shows as a select); the
story declares only the telemetry knobs. Named `const` PascalCase exports, no
default export. Nothing that exists only for a story may be added to
`features/preview/`. Everything else — the seed, scenarios, which states to cover,
history widgets — is in [widget-stories.md](widget-stories.md).

> _Enforced by:_ a missing `PANEL_WIDGET_IDS`, or a second export beside it, is
> silent — the widget simply has no panel, or the wrong one. Together with steps
> 1 and 7 this is the third place the route fails quietly rather than loudly.

## Step 9 — The hot/cold split, if you declared a hot field

If your manifest declares `carDynamics`, `carInputs`, `carPositions` or
`lapDelta`, [rendering.md](rendering.md) is required reading before you write the
component, not after. There is no runtime check for this rule — it is
enforced by review, not by a test — so getting it right the first time is the
whole game.

- A component that reads a hot field returns as little as possible; everything
  that does not change while that field does is lifted into a parent that never
  re-renders and passed down as `children`.
- When the changing value is a single number per frame, skip React entirely and
  write it through `useReactiveDomWrite` (`shared/hooks/useReactiveDomWrite.ts`) —
  see the compass ring in `rendering.md` for the worked example.
- Splitting a component into more, smaller pieces does not help: every child
  still gets a `jsx()` call and an element allocation from its parent on every
  frame, whether or not `observer` then skips its body.

## Step 11 — Run it in the app and look at it

A green suite is not the finish line. The widget has to render under `--wfs`
scaling, over a transparent always-on-top overlay, in a window that is not
Storybook's. Everything before this step is necessary and none of it is that.

```bash
npm run tauri:dev
```

Then drive it through the Tauri MCP bridge — `driver_session` (action `start`,
port 9223), then `webview_screenshot`, `webview_find_element`,
`webview_interact`. Never test the UI in a plain browser: the overlay's
transparency, its scaling and its window are the things being checked.

Look for the four failures that only appear here — one per quiet step:

1. **Empty widget** — a gated field read but not declared (step 1).
2. **Raw i18n keys** where labels belong (step 7).
3. **No settings panel**, or the wrong one (step 8).
4. **Wrong scale** — a `rem`, a `vw`, a raw px where a token belonged, or a
   `WidgetPanel` pinned at its default 200px `minWidth` (steps 3 and 4).

> _Enforced by:_ nothing. This step is a habit, and it is the one that catches
> what the suite cannot.

## Step 12 — Put it in the README and on the site

A widget nobody can find has not shipped. The README and the website gallery
show every widget, from one set of pictures in `site/assets/widgets/` —
transparent PNGs at 3x, taken from Storybook by a script. Nothing collects any
of this; it is three edits by hand.

1. **The picture.** It is taken from the widget's story, so write the story
   the picture should show — seeded the way the widget looks in a race — and
   add the widget to `SHOTS` in `scripts/capture-widgets.mjs` (file name →
   story). A widget that draws a history needs a burst of frames after mount:
   `withReplay` from `src/storybook/with-replay.tsx`. Then, with
   `npm run storybook` running, `npm run capture:widgets -- <file>`
   ([widget-screenshots.md](widget-screenshots.md)).
   It also refreshes the site's WebP copies in `site/assets/img/`; commit
   them with the PNG.
2. **The README.** A `### <Name>` section in the widget's group: one or two
   sentences on what it shows, then
   `<img src="site/assets/widgets/<file>.png" alt="<Name>" width="…">` with
   the width a third of the PNG's — the widget's own size. And a link to the
   section in the group's line at the top of **Widgets**.
3. **The site.** One card in the gallery sheet in `site/index.html`, in the
   widget's group — one per widget, the README's variants stay in the README:
   copy a neighbour's `<li>` and change `id`, `data-shot`, `data-name`,
   `data-alt`, `data-group`, `data-desc-id` and the caption. The description
   itself goes once into the catalogue under the gallery (`<details
class="catalog">`): a `<div class="catalog-item">` in the same group with
   `<dd id="gw-desc-<file>">`, the id `data-desc-id` points at. Then
   `npm run i18n:sync` in `site/` and the new strings translated in
   `site/i18n/ru.json`, `es.json`, `zh.json` — the widget's name stays
   English, as it does in the app.

> _Enforced by:_ nothing.

## The short version

1. Does the field exist, at what rate, is it gated → `telemetryEvents` and
   `requiredCapabilities`
2. Store, or no store
3. Design size, layout knobs, decomposition, and **which branch** the hot reader
   is on — `useReactiveDomWrite`, or a shell/body split
4. Read [the toolbox](widget-toolbox.md) before writing a helper
5. Settings schema, then manifest defaults
6. `manifest.ts` and `mount.ts`
7. Strings in `src/locales/{en,es,ru,zh}/widgets.json` — all four
8. Settings panel (one component, plus `PANEL_WIDGET_IDS`) and a story
9. The hot/cold split, reviewed against `rendering.md`, if a hot field was declared
10. `typecheck`, `lint`, `test`
11. `tauri:dev`, and look at it
12. Picture, README section, site card

The steps nothing enforces: **1** (declaring what you read), **7** (strings),
**8** (the panel registering), **11** (looking at it), **12** (documenting it).
Everything else fails a command.
